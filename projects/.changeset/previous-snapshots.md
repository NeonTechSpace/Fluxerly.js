Handlers of an update or delete event now receive the cached value from before the change, as `previous` on the `EventContext` that `client.on` handlers, `runBot` handlers and event middleware receive in both APIs, so edit and deletion logs can show what changed. The `messageUpdate` and `messageDelete` events read the message cache, `guildMemberUpdate` and `guildMemberRemove` the member cache, `guildRoleUpdate` and `guildRoleDelete` the role cache, `guildChannelUpdate`, `guildChannelDelete`, `threadUpdate` and `threadDelete` the channel cache, and `guildUpdate` and `guildDelete` the community cache. The snapshot is the frozen value the client's own cache held just before it applied the event, never fetched. It is `undefined` when that cache category is not enabled, the cache never saw the entity, or the entry expired or was removed, and for every other event. A queued event keeps its snapshot in memory until its handler runs or the event is dropped, and `maxPendingBytes` does not count it. The test clients deliver it the same way when their cache option is enabled

The new `PreviousSnapshots` interface lists the snapshot type per event, and the new `PreviousSnapshot<K, M>` type gives the type of `previous` for one event. `EventContext` now takes optional type parameters for the event and message type, and `EventInvocationOf.context`, `BotEventContext.context` and the `client.on` handler's context are typed for their event. A helper that takes a plain `EventContext` still accepts any handler's context, including one from a client with `messageFields`, and a context built by hand, such as in a unit test, can leave `previous` out
