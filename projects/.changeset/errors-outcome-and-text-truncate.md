Three additions to the shared `errors` object and the `text` helper, plus two fixes.

The new `errors.outcome(error)` function returns whether a failed request may have reached Fluxer, as `"notDispatched"`, `"rejected"` or `"unknown"`. It reads the `outcome` of any SDK error that has one and, for an Effect `Cause`, the least certain outcome of its failures. It returns `undefined` when the SDK cannot establish an outcome, such as for `CancelledError`, `SdkDefect`, non-SDK values and a `Cause` with a defect, an interruption or a failure without an outcome, so the caller applies its own policy. Only `"notDispatched"` shows that a write was not sent, so treat every other value, including `undefined`, as a write that may have applied and reconcile before sending it again. A `Cause` covers only the failures it kept, and Effect's concurrent `forEach` and `all` drop the reasons of siblings they interrupt, so for several concurrent writes check each item's own result, for example with `{ mode: "result" }`. Wrapping an SDK call in `Effect.timeout` yields only a `TimeoutError`, so use the operation's `timeoutMs` option to keep the outcome.

The new `errors.isNotFound(error, resource?)` function is true for an SDK error with HTTP status 404, including a 404 that `messages.send` reports with reason `rejected`. Pass a `NotFoundResource` such as `"member"` or `"channel"` to also require Fluxer's matching `UNKNOWN_*` code. A 404 says only that the resource is missing, not why: Fluxer answers `UNKNOWN_CHANNEL` for a missing channel and also for message and reaction requests in a thread from a bot that is no longer in the community, while other requests from such a bot get a 403 `missingPermissions`. A 404 without a recognized code is true without a resource and false with one. Any other resource name throws `HelperError` with operation `errors.isNotFound` and the new reason `resource`. The `NotFoundResource` type is exported from both entry points.

The new `text.truncate(content, { maxLength, suffix? })` function shortens text to at most `maxLength` UTF-16 units and ends it with `suffix` (default `"…"`) when anything was cut. It never splits a surrogate pair and does not trim or look for word boundaries. Invalid text or options throw `HelperError` with operation `text.truncate`. The `TextTruncateOptions` type is exported from both entry points.

`ClientClosedError` gains `outcome`, an addition. A REST call ended by a closing client now reports how far it got: `notDispatched` when the client was already closed or the request was still queued, `rejected` when closure came while waiting out a 429 before a retry, and `unknown` when the request was in flight. The outcome is also recorded in `details.outcome`, and an `unknown` outcome adds a hint to check whether Fluxer applied the change before repeating it with a new client. Closures that are not a REST request, such as gateway commands, collectors, waits, counts, member chunks, downloads and connecting, keep `outcome` as `undefined`. The preparation steps of a message send, namely opening a direct message and uploading attachments, count as not sent for the message, so a closure during them reports `notDispatched` for the message request even if the earlier step took effect. A closure that cuts off a read records `details.read` and gets no hint to check for an applied change. The POST reads `messages.search`, `members.search` and `attachments.refreshUrls` count as reads in a closure and in their other failures, so their network and timeout failures are now retryable by `errors.isRetryable`. An OAuth request that closure cuts off in flight still fails with `OAuthError` reason `network` and outcome `unknown`, and a closure during OAuth instance discovery now reports `notDispatched`. A message cleanup closed while a batch waits out a rate limit now reports that batch's `rejected` outcome instead of `unknown`, and a closure between batches already reported `notDispatched`. The constructor takes an optional `{ outcome, read }` object, so existing `new ClientClosedError()` calls are unchanged.

Partitioned `inviteCreate` handlers now order events per community. They previously ignored the invite's nested `guild.id` and `channel.id`, so every invite shared one key and ran one at a time. With `partition: "guild"`, invites of different communities run side by side while one community's invites stay ordered, and a group invite without a community is keyed by its channel.

The embed input documentation now states Fluxer's limit of 6,000 characters of combined embed text per message. The SDK does not check it locally, and exceeding it fails remotely with reason `rejected` and an `invalidFormBody` API error.
