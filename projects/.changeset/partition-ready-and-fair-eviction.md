Partitioned event handlers can now wait for a partition's own setup without holding a handler slot, and a full partitioned queue no longer lets a longer backlog take room from a shorter one. The `partitionReady` option of `client.on` and of a `runBot` event handler (`EventHandlerOptions`, `BotEventOptions`) takes the partition key, and in the default API a signal that aborts when the subscription stops, and returns a promise. In the Effect API it takes the key and returns an Effect that runs with the services available at registration. Before the first waiting event of a key starts, the SDK calls the hook, and the key's events stay in the queue until it settles while other keys keep starting. A hook that returns a plain value marks the key ready at once. Readiness is kept only while the key has waiting or running events, so the next burst after the key went idle calls the hook again, and hooks for different keys run at the same time, so the hook should be a cheap, idempotent check. A hook that throws, rejects or fails reports every waiting event of that key as a failure of its handler, and a later event calls the hook again. Held events count toward `maxPendingMessages`, `maxPendingBytes` and a draining shutdown. The option needs `partition` and otherwise fails with `ConfigurationError` whose `field` is `"partitionReady"`, a new member of the `ConfigurationError.field` union

Dropped events are also counted per event name. `ClientCounters` has the new `eventsDroppedByEvent` member, which counts overflow, closed and collector drops and malformed dispatches whose type names exactly one event, and the `eventsDropped` reason totals are unchanged. Drops that have no known event name appear only in the reason totals, so the per-event sum can be lower. The metric `fluxerly_events_dropped_total` gains an `event` attribute where the event name is known, next to `reason`

Behaviour changes to know about:

- A partitioned handler with `overflow: "dropOldest"`, which is the default for `client.on` and `runBot`, now drops from the longest backlog instead of the oldest waiting event overall. The backlog of the arriving event's key counts the arriving event. When another key has a longer backlog, that key loses its oldest waiting event, with ties going to the key whose oldest waiting event is oldest. Otherwise the arriving event's own key loses its oldest waiting event, or the arriving event itself when that key has none waiting, and this repeats until the arriving event fits. When the arriving event would be discarded anyway, it is the only event discarded. Under `maxPendingBytes` the choice follows the number of waiting events, not their sizes. The Warn record, counters and policy field are the same, but a handler that relied on the globally oldest event being dropped, or on every partition losing events in arrival order, sees different events dropped. Partitioned `commands` delivery follows the same rule. Handlers without a partition and the policies `dropNewest` and `stop` are unchanged
- The partition function now runs when an event is received, instead of when the handler first considers it, so a slow partition function runs on the gateway callback. A throwing function still reports that event's handler as failed
