"@neontechspace/fluxerly": major
---

Threads, forum channels and media channels now have their own channel shapes in both entry points, instead of arriving as `GuildUnknownChannel`. `ChannelType` gains `AnnouncementThread` (10), `PublicThread` (11), `PrivateThread` (12), `Forum` (15) and `Media` (16), and `GuildChannel` gains `GuildAnnouncementThreadChannel`, `GuildPublicThreadChannel`, `GuildPrivateThreadChannel`, `GuildForumChannel` and `GuildMediaChannel`. A thread flattens Fluxer's thread metadata, such as `archived`, `locked` and `autoArchiveMinutes`, and carries the bot's own `membership` when Fluxer reports it. The `isThreadChannel` function selects every thread type. A forum or media channel carries its tags and post settings, each optional because Fluxer leaves them out of some payloads, such as `guildChannelDelete`. Text and announcement channels gain `defaultAutoArchiveMinutes` and `defaultThreadRateLimitPerUser`. The new constants are `ChannelFlags`, `ThreadAutoArchiveMinutes`, `ForumSortOrder` and `ForumLayout`. The `channels.get` and `channels.fetch` methods can return any of these shapes, and `channels.fetchAll` never lists threads

`Permissions` gains `ManageThreads`, `CreatePublicThreads`, `CreatePrivateThreads` and `SendMessagesInThreads`, so `permissionBits` and `guards.requirePermissions` accept their names. `MessageType` gains `ThreadCreated` (18) and `ThreadStarterMessage` (21). `MessageFlags` gains the server-managed bits `HasThread` (32) and `FailedToMentionSomeRolesInThread` (256), which message and webhook send and edit operations reject before dispatch. `Message.thread` holds the thread a message started, and `GuildListSummary.threadsActive` reports whether the bot can use threads in a community. The testing fixtures gain `thread()` and `forumChannel()` with the `WireThread` and `WireForumChannel` types, and `guildCreate()` now includes an empty `threads` list

The new `client.threads` namespace creates, changes, lists and searches threads and manages their members. Its `create` method starts a thread in a text or announcement channel, `createFromMessage` starts one on an existing message, and `createPost` creates a forum or media post with its first message, sending its files in the same multipart request. The `edit` method archives, locks, renames or pins a thread and replaces a post's tags. For reading, `fetchActive` lists a community's active threads, `fetchArchived` reads one page of a channel's archived threads, and `search` reads one page of matching threads, with the first message of each post in a forum or media channel. Every list carries the bot's own `membership` on each thread it joined. A search that Fluxer answers with HTTP 202 while it builds the community's search index returns `{ indexing: true }` without a retry

Thread membership changes through `join`, `leave`, `addMember` and `removeMember`, and thread members are read with `fetchMember`, `fetchMembers` and `iterateMembers`. With `withMember`, each member also carries the user's community membership, decoded with the thread's community from the channel cache or from one extra channel read. Failures are `ChannelOperationError` values whose operation names the `threads` method, and a missing-permission rejection of `create`, `createFromMessage`, `createPost`, `edit`, `fetchArchived`, `search`, `addMember` or `removeMember` lists the permissions that method needs

Forum and media channels can be created and managed through `channels`. Creating a channel accepts `ChannelType.Forum` and `ChannelType.Media` with `availableTags`, `defaultReactionEmoji`, `defaultSortOrder`, `defaultTagSetting`, `flags`, a `topic` of up to 4,096 characters and, on forum channels, `defaultForumLayout`. Text and announcement channels accept `defaultAutoArchiveMinutes` and `defaultThreadRateLimitPerUser` on creation, and `channels.edit` accepts those two settings and every forum setting, including a complete `availableTags` list. On creation, a setting that the chosen channel type cannot have fails with reason `input` before any request. An edit cannot tell the channel's type, so `channels.edit` accepts every setting and leaves that check to Fluxer. Both methods fail with reason `input` before any request when a value has the wrong format or range, such as more than 20 tags, while checks that need the channel or community, such as whether a tag emoji exists, stay with Fluxer. The new `channels.createForumTag`, `channels.editForumTag` and `channels.deleteForumTag` change one tag and return the updated forum or media channel. The `editForumTag` method replaces the tag, so an omitted `moderated` value or emoji resets. A permission rejection of any of the three lists `ViewChannel` and `ManageChannels` in `details.requiredPermissions`

Webhook clients can now reach threads. `WebhookMessageInput` gains `threadId`, sent as the `thread_id` query parameter, and, on new messages, `threadName` to start a forum or media post with up to five `appliedTagIds`. The SDK rejects `threadName` together with `threadId`, `appliedTagIds` without `threadName`, and `threadName` on a reply or forward before any request. The `fetchMessage`, `editMessage` and `deleteMessage` methods take `WebhookMessageOperationOptions` with a `threadId` to reach a message in a thread, and the default API names it `DefaultWebhookMessageOperationOptions`

Thread gateway events now have their own typed events. The `threadCreate` event delivers a `ThreadCreateEvent`, the thread plus `isNewlyCreated`, which is false when the bot joined or was added to an existing thread. The `threadUpdate` event delivers the changed thread, `threadDelete` a `ThreadDeletion` with the thread's ID, community, parent and type, `threadListSync` a `ThreadListSync` with the bot's active threads in a community or in some of its channels, and `threadMembersUpdate` a `ThreadMembersUpdate` with the members who joined and the IDs of those who left. The `"channel"` handler partition keys thread events by their thread. Automatic event filtering suppresses unused thread dispatches, keeps every thread dispatch while the channel cache is enabled and keeps `THREAD_DELETE` while the message cache is enabled

The channel cache now holds threads. A community snapshot fills it with the active threads the bot can view, leaving out a malformed thread with a `gateway.threadSkipped` Warn record instead of failing the snapshot. Thread create and update events store the thread, a thread deletion removes it, and a thread list replaces the cached threads it covers. The `threads.fetchActive` list also enters the cache, while archived pages, search results, forum posts and member reads do not. A change to the bot's own membership of a thread removes that thread, and a completed Resume removes the resumed shard's threads, because Fluxer never replays thread lists. A `channels.fetchAll` result keeps cached threads, and an operation confined to one thread clears only that thread

Deleting a text, announcement, forum or media channel deletes its threads without thread deletion events. The channel cache removes the threads whose parent is the deleted channel, and the message cache removes the messages of every channel in that community, or without community context, that the channel cache does not hold. Without the channel cache that is every such message, because a message does not record its thread's parent. A thread deletion removes the thread's messages

Permission checks now handle threads. A thread has no permission overwrites of its own, because Fluxer calculates its permissions in its parent channel and then grants `SendMessages` in the thread exactly when `SendMessagesInThreads` is granted. The new `PermissionInput.parentChannel` supplies that parent to `permissions.calculate`, which applies the same rule. A thread without its parent, a thread with a different channel as `parentChannel`, and a `parentChannel` beside a channel that is not a thread fail with reason `input`. For a thread, `permissions.fetch` also reads the parent channel under the same deadline. The `guards.requirePermissions` guard now reads the thread and then its parent channel, each from an enabled channel cache before a request, and decides by the same rule, where it previously used only the member's role permissions and ignored the parent channel's overwrites. None of these checks covers whether the member can see a private thread or whether the thread is archived or locked. The guard also denies a command, with the reason "This command cannot check permissions in this kind of channel", when the channel has a type this SDK version does not know and Fluxer reads it without permission overwrites, because such a channel can take its permissions from elsewhere

Message search no longer fails when a result comes from a thread. Fluxer lists the channel of such a result in a separate thread list, which previously made `messages.search` reject the whole page and stopped `messages.iterateSearch`. `MessageSearchResultsPage.threads` now holds those threads as typed thread shapes, each with the bot's `membership` when the bot has joined it, and `channels` keeps the other channels. Each message's channel appears exactly once across `channels` and `threads`. Audit-log pages and `guildAuditLogEntryCreate` events also no longer fail on a forum or media channel change, because its `available_tags` and `default_reaction_emoji` values now decode as `ForumTag` lists and `ForumDefaultReaction` objects, which `AuditLogChangeValue` gains, and `AuditLogPage.threads` lists the threads that the page's thread actions target

Rejections of thread, forum tag and webhook post operations carry a reviewed `apiError`. The new `ApiErrorCode` categories are `threadArchived`, `threadLocked`, `threadAlreadyCreated`, `channelHasThreads`, `invalidChannelType`, `forumTagNamesNotUnique`, `forumTagRequired`, `noTagsAvailable`, `mediaChannelRequired`, `webhookForumTargetRequired` and `webhookThreadNameRequiresForum`, each with a hint that names the fix. The active thread, forum tag, pinned post and thread member limits join `resourceLimit`, and a missing forum tag or thread member joins `unknownResource`. `ApiProviderCode` gains the matching Fluxer codes

Migration: Code that matched `type === "unknown"` for a thread, forum channel or media channel now receives the typed shape, and an exhaustive `switch` over `GuildChannel`, `ChannelType`, `ChannelCreate` or `ApiErrorCode` needs the new cases. A `permissions.calculate` call for a thread passes the parent channel as `parentChannel`. A `gateway.ignoredEvents` list that names a thread dispatch an enabled cache needs, which is any thread dispatch for the channel cache and `THREAD_DELETE` for the message cache, now fails client creation with `ConfigurationError`, so remove the name or turn off that cache. With only the message cache enabled, deleting a text, announcement, forum or media channel now evicts every cached message of its community and every cached message without community context
