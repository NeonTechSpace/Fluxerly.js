A prefix command parser can now explain why it declined a message. The `commands.parseQuoted` parser now returns a new `PrefixCommandParseRejection` with a fixed `reason` for a quote that never closes or a backslash at the end, where it used to return `undefined` and give no hint, and a custom `parse` function can return the same `{ reason }` shape. The router's `onUnmatched` callback, which already handles unknown names and groups typed without a subcommand, receives the reason on `CommandParserRejected` in both entry points, and the Debug `commands.unmatched` record includes it. The router still sends no reply by itself, so a bot decides whether to turn the reason into one. A rejection with an empty or non-text reason or with other keys is reported like any malformed parser result. The commands guide now explains how to opt in to the quoted parser and how to reply to unmatched messages. A direct caller of `commands.parseQuoted` that tests the result for truthiness or reads `args` must now rule out a rejection first, such as with `"reason" in result`, because only a rejection has `reason` and a parse has `name`, `args` and `rawArgs`
