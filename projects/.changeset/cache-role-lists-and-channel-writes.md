Behavior change: A channel write no longer clears the whole channel cache. A write to a cached channel removes only that channel, plus its cached threads when the write deletes the channel or converts its type, and its cached forum posts that apply a tag the write removes, as `channels.deleteForumTag` and a `channels.edit` with `availableTags` can, because Fluxer drops removed tags from posts without a thread update. Removing tags also stops pending reads from storing that forum's posts, while other pending reads by ID and reads of other communities still store what they return. A write to a category, and a write that names a community, such as `channels.create`, `channels.reorder` or `guilds.leave`, removes only that community's cached channels. A write to a channel the cache does not hold still clears every cached channel. Code that relied on the full clear can call `client.cache.clear("channels")` after the write

Behavior change: A `guildChannelUpdate` event for a forum or media channel now removes the channel's cached posts that apply a tag missing from the update's `availableTags`, because Fluxer removes a tag through that update alone and drops it from posts on read. Fluxer gives each new tag a new ID, so posts whose tags all remain stay cached. Every such update also stops pending reads from storing that forum's posts, because a read of the forum can store its new tags before the update arrives. Other pending reads by ID and reads of other communities still store what they return, so an update in one community does not keep an unrelated read from filling the cache, while a pending read of the updated channel's own community stores nothing, as after any channel update

Behavior change: A `guildChannelUpdate` event for a text or announcement channel now removes that channel's cached threads whose type the channel's type cannot hold, because Fluxer retypes a converted channel's threads and sends no thread update for archived ones. This works whether the channel was cached before the update or not, and after a read already stored its new type. Every such update also stops pending reads from storing that channel's threads, while other pending reads by ID and reads of other communities still store what they return

Behavior change: A shard's first session now releases its communities' cached snapshots, as every later new session already did, and stops pending reads from storing them. Community, member, role, emoji, sticker and channel snapshots read through REST before connecting no longer outlast the first READY, because the events between that read and the session were never received. The release happens as READY arrives, before the communities Fluxer then sends again through `guildCreate`, which refill the community, role, emoji, sticker and channel caches. This also fixes later new sessions, which until now could release those communities after they arrived, leaving the caches empty until each community was read again. Read again after connecting to keep other snapshots, such as members. A saved session resumed through `sharding.sessions` is not a new session and keeps them

The new `roles.getAll(guildId)` method returns every cached role of a community, including everyone and ordered like `roles.fetchAll`, or `undefined` unless the cache knows the list is complete. A `guildCreate` event makes it complete, as does an uncontested `roles.fetchAll` read that finishes while the community's shard is connected, because only role events keep the list current. A full read that finishes while the community's shard is disconnected therefore does not make the list complete, while a list that was already complete stays complete through a recovery that resumes the session. Role create and update events keep it complete. Removing any of its roles, a new session for its shard and every successful role write by the bot, including create, edit and reorder, or one whose outcome is unknown, make it unknown until the next `guildCreate` or full read. The `roles` cache limit counts the roles of every community together, so a bot in many communities needs a larger `maxEntries` to keep complete lists

The new `members.getSelf(guildId)` method returns the bot's own cached member of a community, or `undefined` when it is not cached or the bot's account ID is not yet known from READY or a `members.fetchSelf` result. With `cache.members` enabled, each `guildCreate` now stores the bot's own member. The `guildCreate` events sent while a session starts list member accounts by ID only, so the SDK completes the bot's own member from READY's account and leaves out the others. A `guildCreate` sent after startup, such as for a community the bot joins or one that becomes available again, lists complete members, and the SDK stores all of them, which are the bot's own and those in voice channels

The new `ShardState.sessionEpoch` field identifies a shard's current gateway session. It is 0 until the shard first starts a new session in this client, so a process that resumes a saved session after a restart reports 0 until that shard next starts a new session. It changes, without repeating, whenever the shard starts a new session, including after a move to a larger plan. A Resume keeps it. A changed value means that shard's community events may have been missed, and Fluxer then sends each community again through `guildCreate`. It is the shard's current value, so an event still waiting in a handler's queue can already see a newer one

The new `EventContext.sessionEpoch` field gives the receiving shard's `sessionEpoch` when the client accepted the event, so an event received before a new session keeps its earlier value even when its handler runs after the new session started. Compare `context.sessionEpoch` per community, not per shard, because one shard serves many communities. Events delivered through the testing entry points carry the epoch of the test gateway's session in the same way

The new `context` field of `BotEventContext` gives each `runBot` event handler, in both APIs and in bots run by `createTestBot`, the same `EventContext` that a `client.on` handler receives, so a `runBot` bot can compare `context.sessionEpoch` per community as well
