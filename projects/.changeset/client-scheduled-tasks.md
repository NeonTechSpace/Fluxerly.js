The new `client.schedule` method runs a task once after `delayMs` or repeatedly with `intervalMs` between runs, owned by the client's lifetime in both APIs, so a `runBot` command, handler or `setup` can start delayed or repeating work without keeping a command slot busy or leaving a timer behind. It returns a `ScheduledTask` whose `close()` cancels later runs. The `delayMs` value is 0 through 2,147,483,647 and `intervalMs` 1 through 2,147,483,647, and a repeating task first runs after `intervalMs` unless `delayMs` is set. Invalid options throw `ConfigurationError` in the default API and die with it in the Effect API. The default API takes a function that receives a cancellation signal, and the Effect API takes an Effect that keeps the caller's services and gets a Scope of its own for each run. Each failed run is reported to the client-level `onError`, or logged at Error with the new code `lifecycle.taskFailed` under the new failure kind `task`, and a repeating task keeps its schedule after a failure. A draining shutdown, including a requested `runBot` stop, lets running tasks finish within `drainMs` and counts them in the drain records' new `tasks` field, and every shutdown cancels the rest, counting the tasks it cut short in one `lifecycle.tasksCancelled` Info record. The test kit's `idle()` and `say` in both APIs also wait for scheduled task runs in progress, while a task still waiting for its time does not hold them up. Scheduling after shutdown began throws `ClientClosedError` in the default API and dies with it in the Effect API. The test clients treat a failed task run without an `onError` hook as an unhandled failure. Tasks are kept in memory only. The commands guide's reminder example now schedules its reply instead of waiting inside the command, and the bot lifetime guide explains scheduled tasks
